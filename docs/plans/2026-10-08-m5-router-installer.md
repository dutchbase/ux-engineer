# Milestone 5: router (`ux-orchestrator`, `ux-verify`) and installer — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** route any UX-shaped request to the right skill at the right scope without starting a large process for small or non-UX work, add the `ux-verify` mode, and ship a safe `npx` installer (`install`, `uninstall`, `doctor`) that puts the skills into Claude Code, Codex and OpenCode project folders with a dry run, conflict detection and rollback.

**Architecture:** the router is text only: a `ux-orchestrator` skill plus a shared routing table; `ux-verify` reuses the existing run/evidence/checks contracts. The installer is TypeScript in `src/install/`, exposed as new commands of the existing CLI (`src/cli.ts`), bundled into `dist/ux.mjs` and copied by the existing sync script to a committed `cli/ux-engineer.mjs` that `package.json` `bin` points to, so `npx github:dutchbase/ux-engineer install` works without an npm publish or a build step.

**Tech Stack:** Node ≥ 24 + native TypeScript (repo), bundled CLI for Node ≥ 18, node:test, esbuild, `claude plugin eval` for trigger evals.

**Spec:** [`docs/design.md`](../design.md) — §3.2, §4.1, §4.2, §5.6, §8.1–§8.5, WP11, WP12.

## Global Constraints

- Node >= 24 native TypeScript for repo code: run `.ts` directly, erasable syntax only, `.ts` import extensions, `node:test`. No new runtime dependencies (only `node:` built-ins in `src/install/`).
- No top-level `bin/` folder in the repo (Claude desktop refuses such a plugin). The executable lives at `cli/ux-engineer.mjs`.
- Files under `skills/*/references/`, `skills/*/scripts/` and `cli/` are generated by `pnpm build && pnpm sync`; never edit them by hand.
- Skill frontmatter: only `name` (equals folder name), `description` (≤ 1024 chars, no unquoted `: `), `license: MIT`. Bodies under ~250 lines. Skills never name one host's tool.
- The plugin never edits application code. The installer writes only inside the computed target skill folders and its own record folder `.ux-engineer/`; it never deletes a file it did not create, and never writes outside the target root (resolve real paths; refuse symlinked target folders that point outside the root).
- Project install is the default; global install only with `--global`. No writes without explicit approval: `--yes`, or a "y" answer on an interactive terminal. `--dry-run` never writes.
- Install targets — project: Claude Code `<root>/.claude/skills/<skill>/`; Codex and OpenCode share `<root>/.agents/skills/<skill>/` (one copy). Global: Claude Code `~/.claude/skills/`, Codex and OpenCode `~/.agents/skills/`.
- Messages to the user follow `shared/policies/writing.md` (ASD-STE100) in skills; CLI output is short plain English.
- Commit messages end with:
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` and `Claude-Session: https://claude.ai/code/session_01AVuqHx1gFmnSahdXcKc4Ja`

## Review Focus

1. A project already has its own skill folder `.claude/skills/ux-audit/` with different content → reported as a conflict, nothing written unless `--force`, and with `--force` the old files are backed up first (Task 4 test).
2. Running `install` twice with the same version → every file `skip-identical`, no backups, record unchanged (Task 4 test).
3. A user edits an installed `SKILL.md`, then runs `uninstall` → that file is kept and listed as modified; untouched files are removed; backups are restored (Task 4 test).
4. `install` in a non-interactive shell without `--yes` → prints the plan, writes nothing, exit code 3 (Task 5 test).
5. "Add an index to the users table" or "rename this variable" → no UX skill fires (Task 3 eval).

### Task 1: `ux-orchestrator` skill and routing table

**Files:**
- Create: `skills/ux-orchestrator/SKILL.md`, `shared/references/routing.md`
- Modify: `scripts/sync-shared.ts` (map entry `ux-orchestrator` ← `shared/policies/writing.md`, `shared/references/routing.md` → `references/`), then `pnpm build && pnpm sync`

**Interfaces:**
- Consumes: existing skills and their names: `ux-setup`, `ux-framing`, `ux-plan`, `ux-flow-design`, `ux-research`, `ux-audit`, `ux-accessibility`, and `ux-verify` (Task 2).
- Produces: skill `ux-orchestrator`; `references/routing.md` is the single routing table that Task 3's evals check against.

Content requirements (design §5.6, §4.1, §4.2):
- `routing.md` — a table: request shape → skill → default scope → required capabilities. At least these rows:
  - "who are the users", "set up UX", new project without `docs/ux/project.json` → `ux-setup` (needs a question tool, else chat).
  - "plan / design the flow / how should X work" → `ux-plan` (scope by size).
  - "small styling or layout change" → `ux-plan` light profile (no files).
  - "what do users say / research / competitors / best practices" → `ux-research`.
  - "audit / check the UX of / test in the browser" → `ux-audit` (needs a browser; without one: code-only, run `blocked` or `incomplete`).
  - "accessibility / WCAG / keyboard / screen reader" → `ux-accessibility`.
  - "verify the acceptance criteria / re-check after the fix" → `ux-verify` (needs a browser and a flow file).
  - "fix it / implement it" → not a UX skill: hand off to the implementing agent with the acceptance criteria or findings that exist.
  - Non-UX work (database, refactor, tests, build, deploy, rename) → no UX skill.
- Distinctions the router must make: audit versus fix, plan versus implementation, UX problem versus visual preference (visual-only taste → at most a light note, defer to the design system or a design tool).
- Rules: an explicit skill named by the user wins; read only `docs/ux/project.json` and the request to decide; never repeat the chosen skill's work; check capabilities first (browser tool, Node for `scripts/ux.mjs`, question tool) and narrow the scope instead of lowering the evidence standard; stop at the agreed budget or a real blocker and report it; one skill at a time unless the request clearly spans two (then name the order: for example `ux-setup` then `ux-plan`).
- Output: one short message naming the route, the scope and anything missing, then invoke the chosen skill. No files written by the router itself.
- `description` triggers: "help with the UX of", "is this good UX", "improve the user experience", "what UX work does this need"; negative: implementation, non-UI work.

- Status follows the existing derivation (missing evidence → `incomplete`). Validate and render; summarize per criterion in ASD-STE100. Never edit application code.

### Task 4: installer core — plan, apply, uninstall

**Files:**
- Create: `src/install/hosts.ts`, `src/install/plan.ts`, `src/install/apply.ts`, `tests/install/plan.test.ts`, `tests/install/apply.test.ts`

**Interfaces:**
- Produces (exact):

```ts
// src/install/hosts.ts
export type Host = "claude-code" | "codex" | "opencode";
export type Scope = "project" | "global";
export function detectHosts(env: { home: string; cwd: string }): Host[];
// claude-code if <home>/.claude or <cwd>/.claude exists; codex if <home>/.codex or <cwd>/.agents exists;
// opencode if <home>/.config/opencode or <cwd>/.opencode exists. Sorted, unique.
export function targetDirs(hosts: Host[], scope: Scope, env: { home: string; cwd: string }): string[];
// project: claude-code → <cwd>/.claude/skills ; codex|opencode → <cwd>/.agents/skills (deduplicated)
// global:  claude-code → <home>/.claude/skills ; codex|opencode → <home>/.agents/skills

// src/install/plan.ts
export type Action = { kind: "create" | "update" | "skip-identical"; target: string; source: string };
export type Conflict = { target: string; reason: "modified-by-user" | "foreign-skill" };
export type InstallPlan = { root: string; recordPath: string; version: string; actions: Action[]; conflicts: Conflict[] };
export function planInstall(opts: { sourceRoot: string; root: string; targets: string[]; skills?: string[] }): InstallPlan;
// sourceRoot = package root containing skills/ and .claude-plugin/plugin.json (version read from it).
// root = cwd (project) or home (global); recordPath = <root>/.ux-engineer/install.json.
// For every file under sourceRoot/skills/<skill>/ (all skills unless `skills` given) and every target dir:
//   target file missing → create; identical bytes → skip-identical;
//   different bytes and the file is listed in the existing record with the recorded sha256 → update;
//   different bytes otherwise → Conflict: "modified-by-user" if listed in the record, "foreign-skill" if not.
// Throws if a target dir resolves (realpath of its nearest existing ancestor) outside root.

// src/install/apply.ts
export type InstallRecord = { version: string; installed_at: string; files: { path: string; sha256: string }[]; backups: { path: string; backup: string }[] };
export function applyInstall(plan: InstallPlan, opts: { force: boolean; now: () => Date }): InstallRecord;
// Throws Error("conflicts: <n> files; use --force to overwrite") if conflicts and !force.
// With force, copies each conflicting file to <root>/.ux-engineer/backup/<ISO timestamp>/<relative path> first.
// Writes create/update/conflict files, merges into the record (paths relative to root), writes recordPath.
export function uninstall(root: string): { removed: string[]; keptModified: string[]; restored: string[] };
// Removes recorded files whose current sha256 matches; keeps and lists changed ones; restores backups;
// removes now-empty skill folders it created; deletes the record when nothing recorded remains.
```

```ts
// src/install/doctor.ts
export type DoctorReport = { locations: { dir: string; skills: { name: string; matchesPackage: boolean }[] }[]; duplicates: string[]; record: { path: string; version: string } | null };
export function doctor(opts: { sourceRoot: string; home: string; cwd: string }): DoctorReport;
// Looks in <cwd>/.claude/skills, <cwd>/.agents/skills, <cwd>/.opencode/skills, <home>/.claude/skills,
// <home>/.agents/skills, <home>/.config/opencode/skills for folders named ux-*; matchesPackage compares
// all file bytes with sourceRoot/skills/<name>; duplicates lists skill names found in more than one location
// that the same host reads. Read-only.
```

CLI behavior (`node src/cli.ts <command>` and `cli/ux-engineer.mjs <command>`):
- `install [--host claude-code,codex,opencode] [--global] [--skills a,b] [--dry-run] [--yes] [--force]`: hosts default to `detectHosts`; if none detected and no `--host`, print "No supported host found. Use --host." and exit 2. Print the plan as lines `create|update|skip  <relative target>` and conflicts as `conflict  <path>  (<reason>)`. `--dry-run` → exit 0, no writes. Without `--yes`: if stdin is a TTY ask "Apply? [y/N]"; otherwise print "Re-run with --yes to apply." and exit 3 (Review Focus 4). After applying, print the counts and the hint: "Run /ux-engineer:ux-setup (Claude Code) or $ux-setup (Codex) in this project." plus the suggested `AGENTS.md` line `Read docs/ux/ before any UI or UX work.` (printed, not written).
- `uninstall [--global] [--yes]`: same approval rule; prints removed / kept-modified / restored.
- `doctor`: prints the report; exit 0.
- `sourceRoot` is found by walking up from the running file until `.claude-plugin/plugin.json` exists; if not found: "Run this command from the ux-engineer package (npx github:dutchbase/ux-engineer)." exit 2.
