# Milestone 1: foundations and `ux-setup` — implementation plan

> **For agentic workers:** tasks are delegated to implementation lanes with self-contained specs. Steps use `- [ ]` checkboxes.

**Goal:** an installable plugin with one working flow: `ux-setup` interviews the user about their product's users and writes a valid `docs/ux/project.json` in the target project.

**Architecture:** spec-only Agent Skills in `skills/`, canonical shared files in `shared/` and `schemas/`, copied into each skill's `references/` by a sync script so a single skill folder stays self-contained. A small TypeScript library validates artifacts and derives run status; no build step (Node native type stripping).

**Tech stack:** Node ≥ 24, pnpm, TypeScript (type-check only), `node:test`, Ajv 2020 + ajv-formats.

**Spec:** [`docs/design.md`](../design.md) — §5.1, §6, §7, §8, §10.2, WP01, WP03, WP04, WP12 (manifest part only).

## Global constraints

- Skill frontmatter uses only Agent Skills spec fields: `name` (equals folder name), `description` (≤ 1024 chars), optional `license`, `metadata`.
- Each `SKILL.md` stays under 500 lines. References are one level deep (`references/<file>`).
- No top-level `bin/` folder (Claude desktop refuses the plugin).
- Skills never name a single host's question tool; they say "the host's question tool".
- Every message from a skill to the user follows `shared/policies/writing.md` (ASD-STE100).
- The plugin never edits application code. `ux-setup` writes only under `docs/ux/` and proposes (never applies without approval) one pointer line in `AGENTS.md`.
- Files under `skills/*/references/` that come from `shared/` or `schemas/` are generated by `pnpm sync`. Never edit them by hand.
- Runtime dependencies: `ajv`, `ajv-formats` only. Dev: `typescript`, `@types/node`.

## Review focus

1. A persona attribute without a source is accepted as valid → validator must reject it (Task A tests).
2. A persona with `proto: false` but no `user_data` source → validator must reject it (Task A tests).
3. A required check with result `pass` but no evidence → status must be `incomplete`, not `passed` (Task A tests).
4. Running `ux-setup` when `docs/ux/project.json` already exists → the skill updates it and does not re-ask answered questions (Task B skill text + Task E eval).
5. The host has no question tool and no Brainstormform → the skill asks in plain chat in small batches (Task B skill text).

## Task A: package, contracts, validator, status logic, CI — lane: Luna, `high`

**Files:** `package.json`, `tsconfig.json`, `schemas/project.schema.json`, `schemas/checks.schema.json`, `src/contracts/validate.ts`, `src/contracts/verdict.ts`, `src/cli.ts`, `tests/contracts/validate.test.ts`, `tests/contracts/verdict.test.ts`, `tests/fixtures/project/*.json`, `.github/workflows/ci.yml`.

**Interfaces:**

```ts
type Kind = "project" | "checks";
type ValidationError = { path: string; message: string };
type Result<T> = { ok: true; data: T } | { ok: false; errors: ValidationError[] };
export function validateArtifact(kind: Kind, input: unknown): Result<unknown>;

type CheckResult = "pass" | "fail" | "not_run" | "not_applicable";
type Check = { check_id: string; required: boolean; result: CheckResult;
  not_applicable_reason?: string; actual_result?: string; evidence_ids: string[] };
type RunStatus = "passed" | "needs_work" | "incomplete" | "blocked";
export function deriveRunStatus(checks: Check[], ctx: { blockers: string[] }): RunStatus;
```

CLI: `node src/cli.ts validate <kind> <file>` → exit 0 and prints `valid`, or exit 1 and prints one error per line as `<path>: <message>`.

**project.json schema** (JSON Schema 2020-12, `additionalProperties: false` on every object):

- `schema_version`: `"1.0"`. A different major (`2.x`) → error `unsupported schema major`.
- `product_id` (kebab-case), `product_name`, `product_locale` (BCP 47 like `en-GB`), `updated_at` (date-time).
- `personas[]`: `persona_id` (kebab), `label` (a role, e.g. "First-time shop owner"), `proto` (bool), `summary`, `goals[]`, `context`, `knowledge`, `devices[]`, `frustrations[]`, `sources[]` of `{ attribute: "summary"|"goals"|"context"|"knowledge"|"devices"|"frustrations", kind: "interview"|"web_research"|"user_data"|"assumed", ref: string|null, validation: string|null }`.
- `jobs[]`: `job_id`, `persona_ids[]`, `statement`, `success_outcome`.
- `flows[]`: `flow_id`, `name`, `persona_ids[]`, `file` (string or null).
- `tone`: `voice`, `use[]`, `avoid[]`, `notes` (string or null).
- `accessibility`: `target` enum `"WCAG 2.2 A" | "WCAG 2.2 AA" | "WCAG 2.2 AAA"`, `notes` (string or null).
- `viewports[]` (min 1): `name`, `width`, `height` (positive integers).
- `design_system`: `kind` enum `design_md | tokens | component_library | none`, `path` (string or null), `notes` (string or null).
- `decisions[]`: `decision_id`, `date` (date), `decision`, `reason`, `source`, `decided_by` enum `user | agent`, `kind` enum `general | ai_tell_override`.
- `open_questions[]`: strings.

**Semantic checks in `validateArtifact("project")`** (after schema validation; reported like schema errors):

1. Every persona attribute that is non-empty has at least one `sources[]` entry for that attribute.
2. A source with `kind: "assumed"` needs a non-empty `validation`.
3. `proto: false` requires at least one source with `kind: "user_data"`.
4. `persona_ids` in jobs and flows refer to existing personas.
5. `design_system.kind: "none"` requires `path: null`; any other kind requires a non-null `path`.

**checks.json schema:** `schema_version: "1.0"`, `run_id`, `checks[]` matching `Check` above. Semantic check: `result: "not_applicable"` requires a non-empty `not_applicable_reason`.

**`deriveRunStatus` rules, in order:**
1. `blockers.length > 0` → `blocked`.
2. Consider required checks whose result is not `not_applicable`. If there are none → `incomplete`.
3. Any of them `not_run`, or `pass`/`fail` with empty `evidence_ids` → `incomplete`.
4. Any `fail` → `needs_work`.
5. Otherwise `passed`.

**Tests (node:test), each must fail before the implementation exists:**
- valid full project fixture → ok; minimal valid project (one persona, one viewport, `design_system.kind: none`) → ok.
- unknown top-level field; unknown nested field; wrong enum; schema_version `2.0` (message contains `unsupported schema major`).
- persona goal without a goals source; assumed source without validation; `proto: false` with only interview sources; job pointing to a missing persona; `design_system.kind: tokens` with null path.
- checks: `not_applicable` without reason → invalid.
- verdict: blocker → blocked; required `not_run` → incomplete; required `pass` with no evidence → incomplete; required fail with evidence → needs_work; only optional checks → incomplete; all required pass with evidence plus a `not_applicable` required check with reason → passed; optional failing check does not change `passed`.
- CLI: valid fixture exit 0; invalid fixture exit 1 with `<path>: <message>` lines.

**Scripts:** `test` → `node --test tests/`; `typecheck` → `tsc --noEmit`; `validate` → `node src/cli.ts validate`. CI (GitHub Actions, ubuntu, Node 24, pnpm): install, typecheck, test.

**Verification:** `pnpm install && pnpm typecheck && pnpm test` all green.

## Task B: skill content — lane: Luna, `high`

**Files:** `shared/policies/writing.md`, `shared/references/interview.json`, `skills/ux-framing/SKILL.md`, `skills/ux-setup/SKILL.md`.

- `writing.md`: ASD-STE100 rules for messages to the user (short sentences: ≤ 20 words for instructions, ≤ 25 otherwise; one idea per sentence; active voice; imperative for instructions; simple tenses; one word per meaning; common words, no idioms; quote code, paths and errors exactly). Applies to chat, questions, summaries; not to JSON or code. For non-English report languages, apply the same principles. Cite https://www.asd-ste100.org/.
- `interview.json`: a Brainstormform spec (`title`, `intro`, `categories[]` with `questions[]`; see `brainstormform guide` for the format) with stable ids. Categories: product (name, what it does, locale), customers (who, how many types, what they try to achieve, context and moment of use, knowledge level, devices, frustrations, what makes them leave), evidence (what real user data exists and where; `showIf` follow-ups), tone (voice, words to use/avoid), accessibility target (default WCAG 2.2 AA), screen sizes (defaults phone 390×844, tablet 820×1180, laptop 1440×900, wide 1920×1080; allow additions), design system (kind + path), key flows (top 3 tasks). Every question has a plain-language `explanation`. Max ~25 questions.
- `ux-framing/SKILL.md`: the framing method from design §5.1: personas first; source weights (interview > web research > proto-guess); source per attribute; proto-persona labeling; no human names, ages, photos or quotes without a source; separate stored data, business meaning and user understanding; small tasks get small answers. Output: entries for `docs/ux/project.json` that follow `references/project.schema.json`. Include a compact field guide and one short example persona (proto, with sources).
- `ux-setup/SKILL.md`: user-invocable entry. Steps: (1) read `docs/ux/project.json` if it exists, and the repo's README/AGENTS.md for product context; never re-ask what is already known; (2) look for a design system (`DESIGN.md`, token files, component library) and ask to confirm; (3) interview: if Brainstormform is available (MCP tool `ask_questions` or CLI `brainstormform`), run `references/interview.json` with already-known answers removed; else use the host's question tool in batches of at most 4; else ask in plain chat, at most 4 questions per message; (4) optionally offer web research on the market (cite sources, mark `web_research`); (5) build personas with `ux-framing` rules; (6) write `docs/ux/project.json` and a generated `docs/ux/README.md` (header: "Generated from project.json. Do not edit."); (7) self-check the JSON against `references/project.schema.json` and the five semantic rules; (8) show the user a diff proposal for one line in `AGENTS.md`: "Read `docs/ux/` before any UI or UX work."; apply only on yes; (9) summarize in ASD-STE100: what was written, which personas are proto, open questions. Never write outside `docs/ux/` except the approved AGENTS.md line.
- Both skills reference `references/writing.md`, `references/project.schema.json`; `ux-setup` also `references/interview.json`. These are copied there by Task D.
- Descriptions: specific triggers ("set up UX for this project", "create personas", "who are the users") and negative triggers ("not for small styling changes").

**Verification:** `npx --yes skills-ref validate skills/ux-framing` and `skills/ux-setup` pass (after Task D copies references); `interview.json` is valid JSON and `brainstormform ask shared/references/interview.json` would accept it (check by starting and immediately stopping, or by schema reading of `brainstormform guide`).
